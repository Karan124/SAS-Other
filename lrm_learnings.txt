# LRM Learning File — Azure OpenAI / Westpac Internal Gateway Connectivity

## Purpose
This file captures the end-to-end learnings from the setup and troubleshooting journey for connecting a local Windows workstation to Westpac’s OpenAI/Azure OpenAI environment from Python and VS Code.

It is written for a large reasoning model (LRM) so that it can:
- understand the environment and constraints
- avoid previously failed paths
- reproduce the final working setup
- know which settings are critical vs optional
- understand the rationale behind each decision

This proves:
- Python environment works
- Azure authentication works
- proxy/certificate routing works
- the internal endpoint works

## 4. Critical lessons learned

### 4.1 Use PowerShell, not Git Bash
PowerShell is the only shell that reliably picked up:
- Forge / Artifactory settings
- proxy settings
- certificate settings
- Azure CLI behaviour

Git Bash / MINGW caused issues including:
- broken virtual environment activation syntax
- missing Forge environment variables
- `uv` and `pip` trying to use public PyPI instead of Artifactory
- certificate failures that did not occur in PowerShell

### 4.2 Forge helped for Python package installation, but not enough for Azure auth by itself
Forge already handled much of the local developer environment, including:
- Python installation
- pip / uv default index configuration
- some cert / Artifactory plumbing

However, additional manual work was still needed for:
- VS Code extension marketplace connectivity
- Azure CLI authentication
- corporate certificate trust for `az login`
- proxy routing to the correct OpenAI endpoint

### 4.3 The system / user-level Python install ended up being better than the venv for the CLI path
The workflow started with a `.venv`, but the engineer later requested a system-style install rather than a virtual environment.

The final successful run showed package stack traces from:
- `C:\Users\m061400\AppData\Local\Programs\Python\Python312\Lib\site-packages\...`

This implies the effective working path used:
- user-level / system-style Python packages
- not the venv-local package tree for the final successful OpenAI call

### 4.4 `az login` originally failed because of corporate certificate trust
Initial `az login` attempts failed with:
- `CERTIFICATE_VERIFY_FAILED`
- `unable to get local issuer certificate`

This was due to Azure CLI / Python / MSAL not trusting the corporate proxy certificate chain.

### 4.5 Corporate CA was required
The Westpac CA file had to be retrieved from internal Bitbucket and saved locally as `cacert.pem`.

Worked-from knowledge:
- missing `cacert.pem` was a hard blocker
- without it, Azure CLI authentication could not progress

### 4.6 Successful auth path required system-style install + cert bundle + proxy routing
Eventually `az login` worked after:
- building the correct cert trust setup
- using the right Python/package location
- using the correct proxy settings
- moving away from failed venv-only / MSAL edge-case combinations

### 4.7 The original Azure resource endpoint was not the final working endpoint for Python
Several attempts used:
- `https://t3-a00c3d-cin03-arg01-openai01.openai.azure.com`

This led to:
- timeouts
- proxy / routing confusion
- private IP resolution without successful end-to-end response

The **final successful endpoint** was:
- `https://ai.eng.azure.srv.westpac.com.au`

### 4.8 Do NOT disable proxy usage in the Python HTTP client
A failed script used:
- `httpx.Client(trust_env=False, timeout=60.0)`

This explicitly disabled environment proxy usage.

That caused timeouts because the request path needed to use the normal environment proxy setup.

The engineer explicitly said to remove this and not include `.openai.azure.com` in `NO_PROXY`.

### 4.9 Clear `NO_PROXY` / `no_proxy`
A key learning from the engineer:
- do **not** exempt `.openai.azure.com` from proxy routing
- clear `NO_PROXY` and `no_proxy` before testing

Final successful session included:
- `Remove-Item Env:NO_PROXY -ErrorAction SilentlyContinue`
- `Remove-Item Env:no_proxy -ErrorAction SilentlyContinue`

### 4.10 Keep `HTTP_PROXY` and `HTTPS_PROXY` set for the successful call
The final successful run used:
- `HTTP_PROXY=http://127.0.0.1:9000`
- `HTTPS_PROXY=http://127.0.0.1:9000`

This means the successful OpenAI call travelled through the expected corporate proxy path.

### 4.11 Pinging the original endpoint to a private IP was informative but not sufficient
A ping to the original Azure resource endpoint resolved to:
- private IP `10.54.130.20`
- ICMP timed out

Interpretation:
- DNS / private endpoint routing was present
- but ping timeout alone was not meaningful
- actual HTTPS connectivity still depended on the correct routed endpoint and proxy path

### 4.12 The correct subscription matters
Login initially defaulted to the wrong subscription.

The correct subscription for the innovation environment was:
- `cst-a00c3d-cin03`

A successful testing flow required explicitly setting the correct subscription before running tests.

## 5. Failed or misleading paths to avoid

### 5.1 Avoid Git Bash / MINGW for this workflow
Problems observed:
- venv activation issues
- missing Forge env vars
- `uv` trying public PyPI
- cert problems

### 5.2 Avoid the WindowsApps Python shim in VS Code
Do not select:
- `C:\Users\m061400\AppData\Local\Microsoft\WindowsApps\python.exe`

Use the real interpreter instead.

### 5.3 Avoid using the raw Azure OpenAI endpoint in the script once the gateway endpoint is available
When the engineer provided:
- `https://ai.eng.azure.srv.westpac.com.au`

that became the correct endpoint to use for successful corporate routing.

### 5.4 Avoid `trust_env=False`
This disables proxy usage and caused timeouts in this environment.

### 5.5 Avoid keeping `.openai.azure.com` in `NO_PROXY`
The engineer specifically called this out.

### 5.6 Avoid assuming the standard Azure CLI Program Files path exists
The engineer referred to a path similar to:
- `C:\Program Files (x86)\Microsoft SDKs\Azure\CLI2\...`

That path was not present because the user’s Azure CLI install path differed.

### 5.7 Avoid assuming `az login` cert fixes work the same in all install modes
There were multiple complications involving:
- pip-installed Azure CLI in a venv
- system/user-level install behaviour
- MSAL certificate handling

The final auth path required iterative fixes and cannot be assumed trivial.

## 7. Final known-good Python script

Use a script equivalent to the following:

```python
from azure.identity import DefaultAzureCredential, get_bearer_token_provider
from openai import AzureOpenAI

endpoint = "https://ai.eng.azure.srv.westpac.com.au"

token_provider = get_bearer_token_provider(
    DefaultAzureCredential(),
    "https://cognitiveservices.azure.com/.default"
)

client = AzureOpenAI(
    azure_endpoint=endpoint,
    api_version="2024-10-21",
    azure_ad_token_provider=token_provider,
)

response = client.chat.completions.create(
    model="gpt-5.4-mini",
    messages=[
        {"role": "system", "content": "You are a helpful assistant."},
        {"role": "user", "content": "Say hello in one sentence"}
    ]
)

print(response.choices[0].message.content)
```

### Important notes on the script
- Use **base endpoint only**:
  - `https://ai.eng.azure.srv.westpac.com.au`
- Do **not** append `/openai` or `/openai.com`
- Do **not** supply a custom `httpx.Client(trust_env=False, ...)`
- Let the SDK use normal environment proxy behaviour

## 9. Certificate / CA learnings

### Missing cert file was a hard blocker
The file `cacert.pem` was required.

### Source of corporate cert
The engineer provided an internal Bitbucket location for the Westpac root CA.

### Behaviour observed
- without the CA bundle, `az login` failed with SSL trust errors
- multiple certificate bundle paths were investigated
- the exact working path evolved over time
- the final auth success confirms the cert / trust issue was ultimately resolved

### Practical LRM takeaway
If Azure CLI authentication fails in a similar environment with `CERTIFICATE_VERIFY_FAILED`:
1. assume corporate CA trust is missing
2. obtain the organisation root CA / intermediate PEMs
3. ensure the actual runtime Python / requests / certifi path being used by the active install trusts those PEMs
4. ensure proxy env vars are set coherently in the active shell

## 15. Practical troubleshooting heuristics for future LRMs

If authentication fails:
- check `az login`
- check correct subscription
- check cert / CA trust
- check shell (PowerShell only)
- check proxy vars

If Python package install fails:
- prefer PowerShell over Git Bash
- assume Artifactory / Forge env vars may not propagate into Git Bash

If the model call times out:
- check whether proxy was accidentally disabled
- check whether `NO_PROXY` is incorrectly bypassing the endpoint
- check whether an internal gateway endpoint exists and should be used instead of the raw Azure resource endpoint

If an internal gateway endpoint is available:
- use that endpoint first
- let the SDK use environment proxy settings

If the endpoint works only through proxy:
- keep `HTTP_PROXY` and `HTTPS_PROXY` set
- do not use `trust_env=False`
- clear `NO_PROXY`
