ALEX dataset: how we will use it (concise, LRM-ready)
What ALEX is in this PoC
ALEX is an evidence and linkage layer that connects:

Controls (by Control ID) to
Applications (by Application ID) and
Data usage / CDE context (Business Term Name, Critical Rating, Data Usage fields)

It is not the primary source for “what the control does” in narrative terms.
What ALEX will be used for (primary uses)

Control-to-Application coverage


Build a Control_ID → Application_ID mapping (many-to-many)
Produce application coverage outputs:

controls per application
key controls per application
applications with no mapped controls (once Alfabet payment app list is available)




Technology evidence for controls


Strengthen auditability by adding:

the application(s) where the control operates
control assessment rating and status
CDE/Critical Rating context (why it matters)




Process linkage signal (indirect)


Use Data Usage (CDE/CRDE) to extract any process identifiers (for example patterns like 04.03.07 … Data Usage)
Where extracted process IDs match Holocentric L2/L3 IDs:

treat as an additional linkage signal Control_ID → Process_ID (indirect)


If no deterministic match exists, keep it as enrichment only (do not invent links).


Gap and concentration analysis


Identify:

controls covering many apps (platform-level controls)
apps relying on a small number of controls (concentration risk)
critical CDEs with few controls (risk hot spots)



What ALEX will NOT be used for (limits)

CT1–CT28 mapping: do not map controls to CTs using ALEX alone, because it lacks consistent control description text. Use JUNO control descriptions and/or tasks/incidents/issues text for CT mapping.
Lifecycle stage placement: same limitation; use JUNO descriptions and tasks text, not ALEX.
Duplicate/best-of-breed decisions: ALEX supports evidence (apps, ratings) but is not the main semantic source. Use JUNO descriptions and effectiveness/incident signals for final decisions.

Required joins / keys (deterministic)

ALEX.Control ID → JUNO.CTRL_ID (primary join)
ALEX.Application ID → Alfabet.Application ID (when Alfabet is available)
Optional parsing:

Extract process IDs from ALEX Data Usage (CDE/CRDE) and attempt match to Holocentric l2_process_id or l3_activity_id



Minimum outputs to derive from ALEX

Control_ID, Application_ID, Application_Name, Control_Assessment_Rating, Key_Control_Indicator, Critical_Rating, Business_Term_Name
Application coverage summary:

Application_ID → distinct control count
Application_ID → distinct key control count


“Unmapped apps” list (requires Alfabet payment app list):

payment apps with zero mapped controls in ALEX/JUNO



Confidence rules when using ALEX

High confidence:

direct Control_ID join to JUNO
direct Application_ID join to Alfabet


Medium confidence:

process inference via parsed process IDs from Data Usage (CDE/CRDE) with exact ID match


Low confidence:

keyword-only or fuzzy inference from application names or business term names (Requires SME / do not auto-link)
